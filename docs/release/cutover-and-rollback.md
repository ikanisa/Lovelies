# Existing-app cutover and rollback

Lovelies updates the existing Memories app records. The owner confirms no real
customer accounts, photos or subscriptions need migration. Do not create a legacy
import or delete unknown/test data on that basis.

1. Preserve the donor checkout/history, current store artifacts/signing lineage,
   old backend configuration references and the current published policy edition.
   Confirm backup/recovery access before external changes.
2. Qualify the selected Supabase project: additive private schema, non-bypass role,
   no client grants/public media, private buckets, independently scoped secrets,
   verified HTTPS private inference and providers, scheduler, retention, monitoring
   and restore. Record exact source/migration/model/image identities and readbacks.
3. Test the exact signed native candidates as clean installs and in-place upgrades
   from the currently store-installed app. Do not uninstall or clear old state to
   make an update pass. Preserve unused old Keychain/Keystore state until the owner
   separately authorizes retirement; do not import another account's cache.
4. Verify the package/bundle, compatible signing, unused upload numbers, product
   IDs, entitlements, data disclosures, policy/support/deletion URLs and reviewer
   flow. A build or configured listing is not store acceptance.
5. Obtain approval of the concrete backend/release package and rollout before
   deployment/upload/submission. Submit through the existing app records. Use
   internal/TestFlight validation before staged/phased production rollout.
6. Keep old installed clients' supporting services available during the compatibility
   window. New clients use the selected Supabase authority; do not split a single
   account's writes between authorities. With no real legacy data, qualification
   still covers anonymous/test installation and retained local state behavior.
7. Observe enrollment failures, authorization denials, queue age/retries, cleanup
   uncertainty, provider acceptance, crash/ANR, support and store installation.
   Hold expansion for any unauthorized access, wrong recipient, data loss, failed
   deletion fencing, persistent auth failure or unusable core journey.
8. A store rollback is not immediate. Halt staged rollout and keep compatible API
   versions available. Prefer a reviewed forward fix; restore a backup only through
   a rehearsed procedure that reconciles post-backup writes, grants and erasures.
   Never blindly roll back consent/revocation/deletion authority.
9. Retire Memories as an active release source only after both updated listings
   are live, actual installs/upgrades are verified and the agreed observation window
   has passed. Disable old release jobs before separately reviewing service/secret
   retirement. Preserve read-only source, releases, notices and recovery evidence.

Launch/monitoring owners, observation duration, backup schedule/restore rehearsal,
alert destinations and final rollout percentage are operating inputs still to
confirm. No old repository, service or secret has been removed by this package.
